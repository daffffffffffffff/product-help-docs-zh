# 文档类型与模板

按读者“此刻要做什么”分类。判断不了时问自己两个问题：

- 读者要**做事**，还是要**理解**？
- 读者在**学**（第一次接触），还是在**干活**（已经会用，要解决一件事）？

| | 学 | 干活 |
|---|---|---|
| 做事 | 快速上手（教程） | 操作指南 |
| 理解 | 概念解释 | 参考 |

最常见的错误是把快速上手和操作指南混写：快速上手里给了三种做法让新手选，或者操作指南里从“什么是同步”讲起。发现混写就拆开，用链接互相指向。

---

## 快速上手（教程）

读者是新手，你要对他的成功负责：每一步都必须能走通。

- 开头一句话说明做完能得到什么，最好是看得见的结果（例如托盘图标变成绿色对勾）。
- 只给一条路径，不给备选方案，不讲原理。原理放到概念解释页，并在结尾链接过去。
- 每一两步给一次反馈：“你会看到……”
- 结尾告诉读者已经完成了什么，并给 1～3 个“接下来可以看”的链接。

```markdown
# 快速上手：<几分钟>完成<第一件事>

完成本教程后，你将<看得见的结果>。

开始前请准备：<账号/系统版本/安装包>

1. <动作>。
2. <动作>。你会看到<反馈>。
3. ……

你已经<完成了什么>。

接下来可以看：[<操作指南 A>](…)、[<概念解释 B>](…)
```

## 操作指南

读者已经会用，带着具体目标来。他关心的是怎么把事办成，对功能介绍不感兴趣。

- 标题写成“如何<做成某件事>”，用读者的目标命名，不用功能名命名（“如何把文件发给同事”优于“共享链接功能”）。
- 第一段只写前提和适用范围：谁能用、哪个版本、要先做什么。
- 步骤编号，一步一个动作；有分支时写“如果……，请……”。
- 限制和付费差异写在相关那一步的子项里。
- 撤销、取消、出错时怎么办，放在最后单独一小节。
- 不解释基础概念，需要时链接到概念解释页。

```markdown
# 如何<目标>

<一句话：做完能达到什么。>适用于<版本/平台/权限>。

1. <动作>。
2. <动作>。
   - <这一步的限制或差异>
3. <动作>。

## 取消/撤销<目标>

<步骤>

## 遇到问题

- <现象>：<原因和处理>
```

## 参考

读者在干活时来查一个事实：上限是多少、图标什么意思、某个选项做什么。

- 只描述，不指导。要指导的内容放到操作指南里并链接。
- 结构跟产品结构走（按设置页面、按菜单），方便对照查找。
- 用表格，格式全篇一致。这里要求完整：列出所有项，不只列常用项。
- 版本差异用列对比（免费版 | 专业版）。

```markdown
# <对象>说明

| 项目 | 说明 |
|---|---|
| <名称> | <含义/取值/默认值> |
```

## 概念解释

读者想知道“为什么”：为什么会生成冲突副本？为什么不能延长链接？

- 讲原因、设计取舍和限制，可以对比不同做法。
- 不写操作步骤，需要时链接到操作指南。
- 只写用户提供的原因。原因不明时标 `【待确认】`，不要猜设计意图。

## FAQ（常见问题）

FAQ 是入口，不是正文。每条只给简短答案，详细步骤链接到操作指南。

- 问题用读者的原话写，带上他看到的现象：“托盘图标变成黄色感叹号怎么办？”
- 答案第一句直接回答，第二句给链接或下一步。
- 按场景分组（安装登录、同步、分享、账号与付费），每组不超过 10 条。

```markdown
### <读者原话式的问题>？

<一句话答案>。详见 [<操作指南>](…)。
```

## 更新说明（Release Notes）

读者想知道：这次有什么变化，和我有没有关系，要不要做什么。

- 按“新增 / 改进 / 修复 / 行为变化”分组。行为变化最重要，要写清楚“以前怎样，现在怎样”，必要时附迁移步骤。
- 每条从用户能感知的结果写起，不写内部实现。
- 只写已上线的内容；计划中的功能要写明“计划”，不能写成已完成。

```markdown
# <产品> <版本>（<日期>）

## 行为变化
- <对象>：以前<旧行为>，现在<新行为>。<需要用户做什么>

## 新增
- <功能>：<能做什么>。详见 [<文档>](…)。

## 修复
- 修复了<现象>的问题。
```
